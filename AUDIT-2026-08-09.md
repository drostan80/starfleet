## Findings

Ordered by severity. **(mine)** marks a defect introduced by yesterday's

### 0. Every anime show Data bridges in gets **no AniList metadata, permanently and silently**

Found while working out the fix for finding 4. This is the most serious
item in the audit and it reorders the whole plan.

`_fetch_anilist` needs a **show-level** `anilist` `show_external_id`
row. `fetch_and_populate` runs it *before* `_fetch_sonarr`. So for an
anime show added with only a tvdb id:

1. `_fetch_anilist` finds no show-level AniList link → returns early,
   deliberately **without** a `pending_review` ("a caller-input gap").
2. `_fetch_sonarr` → A.20's `_ensure_seasons` → Fribb resolves the
   AniList id correctly and writes it **to the season row**.
3. Nothing ever goes back. `refreshShowMetadata` can't fix it — it
   re-runs the same `_fetch_anilist`, which still finds no show-level
   link.

Verified end-to-end: Fribb resolved AniList id 111 into the season row;
`anilist_client.fetch_media` was called **zero** times; synopsis,
poster, cast, studios and duration all stayed `null` — before *and*
after an explicit `refreshShowMetadata` retry. No review entry anywhere.

**This is the primary production path, not an edge case.** Data's own
`lcars_client.py` documents it: *"`anilist_id` is optional — data's own
add flow often doesn't [have it]"*, and `_track_new_show_on_lcars` calls
`add_show(title=..., tvdb_id=..., is_anime=...)` — **it never passes an
AniList id at all.** So every anime show added through A.17's bridge
today lands permanently bare, while LCARS holds the very id needed to
enrich it one table away.

It also decides finding 4 for us: **hard rejection is off the table** —
it would break Data's bridge outright on every anime add.

### 1. `episode.absolute_number` is never populated — and this makes A.22 inert

§5.2 specifies it in detail: sourced as-is when a source reports one,
otherwise synthesized as `<preceding regular absolute>.<index>` (a
special between S1E12 and S2E1 becomes `12.1`). **Neither half exists.**
Sonarr *does* report `absoluteEpisodeNumber`; A.22 (yesterday) even
reads it — to decide the numbering *scheme* — but never stores it.

Verified: Sonarr reporting absolute numbers 1 and 13 → both episodes
stored with `absoluteNumber: null`.

The compounding problem: A.22 now correctly derives
`episode_numbering_mapping.scheme = absolute` for anime, but there is no
absolute number on any episode for that scheme to address. **A.22 as
built is a label with nothing behind it.**

- **Pro fixing now**: A.22 is dead weight until this exists. The
  source-as-is half is ~3 lines in `_fetch_sonarr`. Phase B's air-date
  and backlog work will assume episode identity is settled.
- **Con**: the *synthesis* half (the `12.1` rule) is genuinely fiddly —
  ordering by air date, handling ties, recomputing when a new special
  lands mid-season. Not a 3-line job.
- **Options**: (a) both halves now; (b) source-as-is now, synthesis
  deferred to a named later step; (c) both deferred, with A.22 explicitly
  marked as pending them.

### 2. `episode.kind` is hardcoded `'regular'` — nothing ever creates `special`/`ova`/`bonus_movie`

§5.2 requires season-0 rows to carry a real `kind`. `_fetch_sonarr`
writes `'regular'` for every episode it imports, season 0 included.

Two downstream consequences, both **future gaps that will surface in
Phase B**:
- **B.3's own text** says "remember `bonus_movie`-kind episodes are
  commonly available via **both** sources" — B.3 is designed around a
  `kind` value nothing produces.
- **`episode_movie_link` (§5.1 addendum) exists to reconcile a
  `bonus_movie` episode against a standalone movie show.** With no
  `bonus_movie` rows ever created, that table can never have a real
  subject. A.14's hard-delete cascade dutifully handles a table that
  will always be empty.

- **Pro fixing now**: cheap (Sonarr's season-0 + its own episode
  metadata is enough to classify), and it unblocks B.3 as written.
- **Con**: the `special`-vs-`ova`-vs-`bonus_movie` distinction may need
  a real rule from you — Sonarr doesn't label it that finely; runtime
  heuristics ("over 60 min → bonus_movie") are a guess.
- **Options**: (a) classify season-0 as `special` now, leave
  `ova`/`bonus_movie` to a rule you specify; (b) full classification now
  with a rule you give me; (c) defer, and annotate B.3 that it must
  build the classifier first.

### 3. `episode_movie_link`'s automated `tmdb_match` derivation is unowned by any step

§5.1's addendum specifies the full reconciliation ("a best guess applies
immediately with a `pending_review` entry on ambiguity, manual override
wins once set"). Only the enum value and the manual mutations exist. I
searched all of Phase A, B, and C — **no step claims it.**

- **Pro**: it is a specified §5 behavior with no owner; unowned work

- **Con**: it is genuinely blocked behind finding 2 (no `bonus_movie`
  rows to match) — building it now means building against nothing, the

- **Options**: (a) add it as a Phase B step, explicitly after the `kind`
  classifier; (b) add it to Phase A after fixing finding 2; (c) record
  it in §9 as deliberately not built.

### 4. §5.1's "anime **mandates** an AniList link, no exceptions" is not enforced anywhere

Verified: `addShow(trackingSpace: ANIME)` with no `anilistId` is
accepted and produces a show with zero external ids.

Worse, migration `7196ca889757`'s own comment asserts the opposite:
*"an application-layer invariant (enforced by addShow/on-demand-fetch,
A.8), not a DB constraint"*. `_fetch_anilist` merely returns early,
calling it "a caller-input gap" — no error, no `pending_review`. **The
codebase documents an enforcement that does not exist.**

- **Pro fixing**: §5.1 says "no exceptions"; an unenforced mandatory
  invariant is how silently-wrong data accumulates. A.21's stubs now
  create anime shows programmatically too, widening the surface.
- **Con**: hard rejection could block a legitimate flow — adding an
  anime show whose AniList id you don't have to hand yet. A
  `pending_review` entry may fit this project's "apply, then flag"
  philosophy (§3 principle 1) better than an outright error.
- **Options**: (a) reject at `addShow`; (b) accept but open a
  `pending_review` (most consistent with §3.1); (c) accept silently and
  correct the migration comment to match reality.

### 5. **(mine)** A.20 creates a permanent, unresolvable `pending_review` for season 0

Verified end-to-end: a show with specials (season 0) plus season 1
produces —

```
season z-0ag69a  season_number 0  source UNMATCHED  matched False
pending_review   entity season z-0ag69a  field anilist_id  chain ['unmatched']
```

Season 0 is the specials bucket (§5.2), not a real season; Fribb will
never map it. So **every episodic show with specials generates one
review entry that can never legitimately resolve.** §5.6 keeps entries
permanently. This directly contradicts the care taken elsewhere to avoid
review noise (A.4's manual-override decision was made specifically to
avoid "review noise for something already manually decided").

It does not compound — a re-fetch does not extend the chain — so it is
one stale entry per show, not a growing pile.

- **Pro fixing**: it is noise in the one queue the whole design routes
  human attention through, and it is my regression.
- **Con**: none I can argue for keeping it.
- **Options**: (a) skip season 0 in `_ensure_seasons` entirely — no
  season row at all; (b) create the season row but suppress the
  `pending_review` for season 0 specifically; (c) treat season 0 as
  legitimately unmatched and accept the entry.
  I'd want your call on whether a season-0 `season` row should exist at
  all, since `episode.season_id` for specials depends on it.

### 6. **(mine)** A.20 re-parses and re-indexes the entire Fribb dataset once per season

`_ensure_seasons` calls `reconcile_season` per season number; each call
independently does `load_dataset()` (full JSON read + parse) plus
`build_tvdb_index()` (full scan). A 5-season show = 5 full parses of a
multi-megabyte file, synchronously, inside a resolver.

Measured on a 3.2 MB / 40k-entry synthetic: **0.06 s per season, 0.30 s
for five.** The real `anime-list-full.json` is several times larger.

This lands squarely on §11.2's own justification for the sync/single-
connection model — *"local SQLite file operations are sub-millisecond"*.
A multi-megabyte JSON parse is not, and it blocks the event loop for
every concurrent client.

- **Pro fixing**: trivial (load + index once per fetch, pass down), and
  it is my regression.
- **Con**: none; at personal scale it is survivable today, which is
  exactly why it would otherwise go unnoticed until Phase B.
- **Options**: (a) hoist the load/index to the caller; (b) memoize
  inside `fribb`; (c) leave, and note it against B.1's concurrency work.

# Recommended paths forward

## Tier 0 — fix first: anime identity resolution (findings 0 + 4)

**Recommendation: resolve the AniList link from Fribb before fetching,
and treat a genuine failure as a `pending_review` — never a rejection.**

Add an `_ensure_anilist_link()` step at the *top* of
`fetch_and_populate`, before any source branch: if `tracking_space =
anime` and no show-level `anilist` link exists, resolve it from the
show's tvdb id via Fribb (season 1 — the same convention `_upsert_season`
and `addShow`'s own `anilistId` input already assume) and write a real
`show_external_id` row. Then the existing `_fetch_anilist` just works,
unchanged, on this run — not the next one.

Why this shape:
- **It reuses machinery that already exists and already works.** A.20
  proved Fribb resolves these correctly; this only applies the answer
  one level up.
- **It makes §5.1's "no exceptions" mandate true** rather than
  aspirational, and lets me delete the migration comment's false
  enforcement claim instead of just correcting it.
- **It self-heals the existing bare shows** — `refreshShowMetadata`
  starts working retroactively for everything Data has already bridged.
- **Reordering is the actual bug.** Identity resolution belongs before
  metadata fetch; today it happens after, which is why the answer
  arrives too late to use.

Fallback when Fribb can't resolve (no tvdb id, or no match): open a
`pending_review` rather than failing. §3 principle 1's "apply, then
flag, never gate" governs, and Data's bridge must not break.

**Alternative I considered and rejected**: making `_fetch_anilist` fall
back to reading season 1's `anilist_id`. Less invasive, but it leaves
§5.1's mandate unsatisfied (no `show_external_id` row) and leaves the
show-level link permanently absent for every other consumer.

## Tier 1 — my regressions and errors (no design input needed)

- **C.1 / finding 5 — skip season 0 in `_ensure_seasons` entirely.**
  Not "create the row but suppress the review". Season 0 is the
  specials bucket (§5.2), not a season with a cross-service identity;
  a `season` row for it is semantically empty. `episode.season_id`
  stays `NULL` for specials, which is the honest answer — the column is
  nullable precisely for this.
- **C.2 / finding 6 — memoize in `fribb.py`, keyed on cache-file
  mtime.** Not merely hoisting the load out to `_ensure_seasons`.
  Hoisting fixes one call site; **B.2 (weekly reconciliation across
  every show) is the real hammer** and would re-parse per season per
  show. Fixing it at the source fixes every present and future caller.
- **C.8 / finding 7 — correct `+9` → `+4`.**

## Tier 2 — episode identity (needs your decisions)

These three interlock, so the order matters more than the individual
choices.

- **C.5 / finding 2 — classify season 0 as `special`, plus add a
  `setEpisodeKind` mutation.** Sonarr genuinely cannot distinguish
  special / ova / bonus_movie, and I'd argue *against* a runtime
  heuristic for `bonus_movie`: a wrong classification has a real
  consequence (§5.2 ties `available_via_radarr` to `bonus_movie`), and
  guessing is how the silent-wrong-data this project keeps catching gets
  in. `special` is conservative, strictly better than today's
  factually-wrong `regular`, and honest. The mutation matters
  independently: **`kind` is currently read-only in the whole API**, so
  there is no way to correct it at all — that also gives `ova` its only
  possible path until automation exists.
- **C.3 / finding 1a — store Sonarr's `absoluteEpisodeNumber`.** Two
  lines, no design input, and it is what makes A.22 mean something.
- **C.4 / finding 1b — synthesis (`12.1`, `12.2`) as its own named
  step, after C.5.** It needs to know which episodes are specials, and
  it should be a **whole-show recompute after each fetch**, not
  incremental — indices shift when a new special lands mid-season. No
  consumer reads absolute numbers until Data does (Phase B/C), so this
  can be scheduled rather than rushed — but it must have an owner.

## Tier 3 — defer, with explicit owners (do not build now)

- **C.6 / finding 3 — `episode_movie_link` auto-`tmdb_match` → a
  numbered Phase B step, after B.3 and C.5.** Building it now means
  building against zero `bonus_movie` rows and no Radarr file data —
  precisely the reasoning A.4 used to defer numbering derivation, and it
  was right then.
- **C.9 / finding 8 — `local` rollup → annotate B.7 explicitly.** Its
  input (`episode.available_locally`) is not populated until B.3, so
  building it now means aggregating over permanently-false data. The
  annotation must say B.7 needs a *rollup* code path distinct from
  A.7's fuzzy-match mutation, and that B.3 must precede it.
- **C.10 / finding 9 — hygiene.** Auto-fix the 22 `noqa` (`ruff
  --fix`), dedupe `_get_season`, and add `RUF100` to the project's
  `select` so this class stays caught rather than being cleaned once.
