# Read-only audit, 2026-10-05

Everything here was measured read-only on a copy of the production database (taken 10-04 from tiny, plus live
read-only queries on prod where noted). **No production data or code was changed.** Fixes mentioned are proposals
unless marked "done in dev".

## 1. 🔴 Special levels are re-created on every Memory Alpha pass (new, found while timing the pass)

- **What:** since the cutover, each Memory Alpha pass (every ~20 min) creates **53 new `special` season rows** — the same
  pieces again. Prod `season` table: **21,798 rows**, of which **18,863** are auto-created specials (a healthy database has
  ~4,900). Created per day: 09-30 3,549 · 10-01 3,419 · 10-02 3,470 · 10-03 3,493 · 10-04 3,454 · 10-05 (to 06:00 UTC) 902.
  E.g. "Alien: Earth Podcast Episode 3" exists **323 times**. 159 pieces are duplicated, across 21 shows (The Last of Us,
  Doctor Who (2005), Alien: Earth, The Expanse, Kakkou no Iinazuke…).
- **Cause (confirmed in the code):** `numbering._special_level` looks for a piece's level under its season
  (`parent_id IS <the season>`); but `_nest_in_minis_groups` (R1.13c) afterwards moves each such piece **into its
  "Season N minis" group**. Next pass the lookup no longer finds it, creates a new one under the season, and the nest step
  moves that one in as well. All 323 copies of the Alien: Earth piece sit under the same minis group.
- **Effects:** the database grows ~3,450 rows (and ~3,400 span rows) a day; show pages of the 21 shows carry hundreds of
  identical level cards (Alien: Earth: 1,351 season rows, 1,365 spans); the hourly weekly-reconcile tried the extra levels
  (part of the 189 daily `reconcileSeasonMapping` failures, already fixed in dev); sweeps get slower (renumber, queries).
  **No external effect found:** the extras are `planned`/`skipped` specials with `list_sync = 0`, no AniList/MAL ids, no
  episodes, no scores or dates, so nothing is pushed anywhere.
- **Cleanup safety, measured on the 10-04 copy:** 14,048 extra rows (keeping the oldest of each group). Of them: 0 hold
  episodes, 0 have list ids, 0 have a score or dates, 0 are parents of other levels, 0 are in a chosen schedule; 16 have a
  status-history row, 844 have a status other than `planned` (they follow their season's status, R2.16 — same as their
  originals). 16,842 span rows belong to them.
- **Proposed (needs your yes):** (a) fix the lookup so a piece nested in a minis group is found (e.g. look it up by its
  code/label under the season **or** its minis group), with a test that two passes in a row create nothing; (b) a data
  patch deleting the extras and their spans/history rows (keep the oldest per show+parent+label), dry-run first.
  **Timing:** this grows by ~3,450 rows a day on prod while we wait for the drip; shipping just this fix + cleanup ahead of
  the bulk release is an option you may want.

## 2. Memory Alpha pass timing (why ops times out at 120 s)

One pass on a scratch copy (AniDB blocked, datasets stale, so it also refreshed datasets), cProfile:

| Part | Time |
|---|---|
| `ensure_fribb_season_rows` → **26 throttled AniList status calls** | **53 s** (of which 43 s is the AniList throttle sleeping) |
| AniDB drip, 5 anime | 16 s here (≈20 s on prod at 4 s pacing + the requests) |
| `numbering.renumber_all` (1,739 shows) | 9 s (will shrink after the duplicate cleanup) |
| everything else | ~16 s |
| **Total** | **94 s** (prod adds its own AniDB time and the 21k-row tables → over 120 s) |

- The 53 s is waste: `ensure_fribb_season_rows` asks AniList for release statuses for every show where Fribb has more
  entries than LCARS has TVDB-season numbers (split cours), **then creates nothing** because the AniList id is already held by
  a part level. It repeats every pass. It also still uses the old "position in Fribb's list = season number" idea (the same
  assumption as the identity check), so under the rebuilt model it could create a phantom season row in some case; it has
  created none since the cutover.
- **Options (your call, "after timing"):** (1) only ask AniList when a row will really be created (removes ~53 s, tiny
  change); (2) raise ops's timeout; (3) both; and later (4) review that function for the rebuilt model.
  After the drip finishes the AniDB part drops out too, so (1) alone would very likely bring the pass well under 120 s.
